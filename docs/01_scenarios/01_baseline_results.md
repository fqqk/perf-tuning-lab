## 🔍 考察：なぜ Go が 8-9 倍高速なのか

### 実行モデルの違い

#### **Node.js（シングルスレッド + Event Loop）**

```
リクエスト1: [CPU計算 100ms] → [I/O待ち 100ms] → 完了
           ↓ Event Loop ブロック中
リクエスト2: [待機................................] 
リクエスト3: [待機................................]
...
リクエスト50: [待機........................................]

結果: リクエストが直列処理される
実測 Latency: ~2.2s（= 200ms × 11リクエスト相当が待機）
```

**ボトルネック:** CPU計算（同期）でイベントループが停止 → 他のリクエスト処理ができない

#### **Ruby（マルチスレッド + GVL）**

```
Process 1
├─ Thread A: [CPU計算 100ms] ← GVL で他スレッド排除
├─ Thread B: [待機.............] 
├─ Thread C: [待機.............]
└─ Thread D: [待機.............]

GVL 解放後に他スレッド処理 → 結果的に直列処理に近い

実測 Latency: ~2.25s
```

**ボトルネック:** Global VM Lock（GVL）で複数スレッドが競合 → CPU計算中は他スレッドが実行不可

#### **Go（M:N スケジューラ + Goroutine）**

```
Goroutine 1: [CPU計算 100ms]  ← 実行中
Goroutine 2: [I/O待ち 100ms]  ← スケジューラが切り替え
Goroutine 3: [別タスク実行]   ← OS スレッドで処理
...
Goroutine 50: [別タスク実行]

全て並行処理 → CPU待ちと I/O待ちが オーバーラップ

実測 Latency: ~254ms（ほぼ理論値 200ms + OS オーバーヘッド）
```

**理由:** Goroutine は I/O待機時に自動的に OS スレッドを譲る → 他の Goroutine が処理可能

## 💡 学習ポイント

### 1. **言語の実行モデルがパフォーマンスを支配する**

同じ処理（CPU 100ms + I/O 100ms）でも：
- **Event Loop ドリブン** → CPU計算でメインスレッド停止 → リクエスト直列化
- **GVL 制約** → CPU計算時に他スレッド実行不可 → リクエスト直列化
- **軽量スレッド（Goroutine）** → I/O待機時に自動切り替え → 並行処理可能

### 2. **計測が全て**

推測ではなく、実際の計測値で言語特性が明確になる：
- Node.js「Event Loop ブロック」← 実測で証明
- Ruby「GVL 競合」← 実測でも競合の影響が顕在（Node.js と同等）
- Go「Goroutine 効率」← 実測で 8 倍の性能差で証明

### 3. **チューニング方向が見える**

ボトルネックが分かれば、対策も明確：
- **Node.js:** CPU計算を worker_threads へオフロード
- **Ruby:** Process 数増加で CPU 複数コア活用 / YJIT 有効化
- **Go:** 既に最適だが、Goroutine Pool で リソース制限 / GC 調整

## 📋 次のステップ

### Scenario 1: チューニング実施（予定）

1. **Node.js: worker_threads 導入**
   - CPU計算を別スレッドへオフロード
   - 期待効果: RPS 向上、Latency 改善

2. **Ruby: Process 数増加 + YJIT 有効化**
   - Process を複数（4個など）に増加 → CPU マルチコア活用
   - YJIT 有効化 → CPU 計算速度向上
   - 期待効果: RPS 向上、Latency 改善

3. **Go: Goroutine Pool 導入**（オプション）
   - 現状でも十分だが、リソース制御の実装例として
   - 期待効果: メモリ使用量 低減、GC 圧力 軽減
