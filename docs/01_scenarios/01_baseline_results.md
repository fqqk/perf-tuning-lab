## 🔍 考察：なぜ Go が 8-9 倍高速なのか

### 実行モデルの違い

#### **Node.js（シングルスレッド + Event Loop）**

```
リクエスト1: [CPU計算 100ms] → [I/O待ち 100ms] → 完了
           ↓ Event Loop ブロック中
リクエスト2: [待機................................] 
リクエスト3: [待機................................]
...
リクエスト50: [待機........................................]

結果: リクエストが直列処理される
実測 Latency: ~2.2s（= 200ms × 11リクエスト相当が待機）
```

**ボトルネック:** CPU計算（同期）でイベントループが停止 → 他のリクエスト処理ができない

#### **Ruby（マルチスレッド + GVL）**

```
Process 1
├─ Thread A: [CPU計算 100ms] ← GVL で他スレッド排除
├─ Thread B: [待機.............] 
├─ Thread C: [待機.............]
└─ Thread D: [待機.............]

GVL 解放後に他スレッド処理 → 結果的に直列処理に近い

実測 Latency: ~2.25s
```

**ボトルネック:** Global VM Lock（GVL）で複数スレッドが競合 → CPU計算中は他スレッドが実行不可

#### **Go（M:N スケジューラ + Goroutine）**

```
Goroutine 1: [CPU計算 100ms]  ← 実行中
Goroutine 2: [I/O待ち 100ms]  ← スケジューラが切り替え
Goroutine 3: [別タスク実行]   ← OS スレッドで処理
...
Goroutine 50: [別タスク実行]

全て並行処理 → CPU待ちと I/O待ちが オーバーラップ

実測 Latency: ~254ms（ほぼ理論値 200ms + OS オーバーヘッド）
```

**理由:** Goroutine は I/O待機時に自動的に OS スレッドを譲る → 他の Goroutine が処理可能

## 💡 学習ポイント

### 1. **言語の実行モデルがパフォーマンスを支配する**

同じ処理（CPU 100ms + I/O 100ms）でも：
- **Event Loop ドリブン** → CPU計算でメインスレッド停止 → リクエスト直列化
- **GVL 制約** → CPU計算時に他スレッド実行不可 → リクエスト直列化
- **軽量スレッド（Goroutine）** → I/O待機時に自動切り替え → 並行処理可能

### 2. **計測が全て**

推測ではなく、実際の計測値で言語特性が明確になる：
- Node.js「Event Loop ブロック」← 実測で証明
- Ruby「GVL 競合」← 実測でも競合の影響が顕在（Node.js と同等）
- Go「Goroutine 効率」← 実測で 8 倍の性能差で証明

### 3. **チューニング方向が見える**

ボトルネックが分かれば、対策も明確：
- **Node.js:** CPU計算を worker_threads へオフロード
- **Ruby:** Process 数増加で CPU 複数コア活用 / YJIT 有効化
- **Go:** 既に最適だが、Goroutine Pool で リソース制限 / GC 調整

## 🔧 Node.js チューニング実施結果

**実施内容:**
- Event Loop ブロック対策：CPU 計算を worker_threads へオフロード
- ワーカープール実装：CPU コア数分の Worker を常時保持
- 並行実行：CPU 計算と I/O 待ちを同時実行

### チューニング後の結果

| 指標 | ベースライン | チューニング後 | 改善率 |
|------|-----------|------------|------|
| **平均 Latency** | 2.22s | 150.61ms | **93% ↓** |
| **P95 Latency** | 3.92s | **204.72ms** | **95% ↓** |
| **RPS** | 7.85 req/s | **21.91 req/s** | **+179%（2.79倍）** |
| **成功率** | 66.14% | **100%** | **完璧** |
| **Threshold** | ❌ Failed | ✅ **Passed** | 完全クリア |

### チューニングが有効だった理由

1. **Event Loop ブロック回避**
   - ベースライン：CPU 計算でイベントループ停止 → リクエスト直列化
   - チューニング後：worker_threads で別スレッド実行 → Event Loop は他のリクエスト処理可能

2. **並行処理の効率化**
   - CPU 計算（worker）と I/O 待機が同時実行
   - 理論値（200ms）に近い実測値（150.6ms）を達成

### 実装上の特徴

- worker.js：CPU 計算用ワーカースレッド
- ワーカープール：CPU コア数分のワーカーを常時保持
- ラウンドロビン：ワーカーへの負荷を均等配分
- Promise.all：CPU と I/O の並行実行管理

## 🔧 Ruby チューニング実施結果

**実施内容:**
- Workers: 1 → 4（GVL 分散）
- Threads: default(0-5) → 4-16（動的調整、高並行対応）
- YJIT: 有効化（CPU 計算高速化）

### チューニング後の結果

| 指標 | ベースライン | チューニング後 | 改善率 |
|------|-----------|------------|------|
| **平均 Latency** | 2.25s | 354.56ms | **84% ↓** |
| **P95 Latency** | 4.17s | 693.74ms | **83% ↓** |
| **RPS** | 7.80 req/s | 18.59 req/s | **+138%（2.38倍）** |
| **成功率** | 65.94% | 94.55% | **+28pt** |
| **Threshold** | ❌ Failed | ⚠️ P95 694ms | 目標 500ms 未達 |

### チューニングが有効だった理由

1. **Workers 4 による GVL 分散**
   - ベースライン：1 Process で全リクエストが GVL 奪い合い
   - チューニング後：4 Process で GVL 影響が 1/4 に削減
   - 効果：約 40-50% の Latency 改善

2. **Threads 4-16 による高並行対応**
   - I/O 待機（100ms）中に他リクエスト処理可能
   - RPS が 2.38 倍に向上

3. **YJIT による CPU 計算高速化**
   - CPU バウンド処理（100ms 計算）が JIT コンパイル
   - 期待値 10-30% の追加高速化

### 制限要因

- **P95 が 693ms で Threshold 500ms を超過**
  - 理由：CPU 1 コア制限 × 50 VU の高負荷
  - 本番環境（CPU 複数コア）なら、さらに改善するはず
  - 現在の設定（workers 4）は実験的；本番は workers 3 が最適
